Metric: ratio of signature size to firmware size. Target: minimise.

Measured against real on-device artifacts:
  signature alone vs kernel+initramfs (29.8 MB) = 0.011%  (1:9,016)

The ratio is NOT a fixed property of ML-DSA-65. Because the signature covers a
644-byte manifest rather than the payload, the numerator is CONSTANT. Ratio is
therefore inversely proportional to payload size and improves without bound:
0.03% for the kernel alone, 0.011% for kernel+initramfs, 0.00001% at 30 GB.

Naive alternative (sign each artifact) scales the numerator with artifact count:
2 artifacts = 6,618 B, N artifacts = N x 3,309 B. The manifest design makes
signature overhead independent of both payload size and artifact count.

Answers the brief's "PQC size penalty" avenue directly: ML-DSA's large
signatures (3,309 B vs ~64 B for ECDSA) are irrelevant to STORAGE in this
architecture. The dominant size cost is the dm-verity hash tree at 0.81% of
payload (8F.1) - 73x larger than the signature, and a SHA-256 cost, not a
post-quantum one.

M2 19,976 B code + M6 18,224 B stack = 38,200 B (8I.7, 8I.8). That is the
real constraint, and it is measured and passing at 29.1% of 128 KB.
